# 会话管理：从 Append-only JSONL、会话树到可替换存储

本文只回答 Pi 会话管理中的几个核心问题：

1. 会话数据保存在哪里，文件中保存了什么。
2. 一段线性对话如何长成一棵树，又如何从旧节点分出新路径。
3. 树上的 entry 有哪些类型，各自承担什么职责。
4. Append-only（只追加）是什么，Pi 如何实现，为什么选择它。
5. 创建、恢复、导航、分支、克隆和压缩等核心操作如何改变会话。
6. 完整会话树如何投影成下一次发送给 LLM 的上下文。
7. `agent` 层提供了哪些可替换接口，`coding-agent` 当前实际使用什么；若要接入数据库，应实现哪一层。

本文聚焦持久化、树结构和恢复语义。消息从 UI 到 Provider 的完整链路可参考[从 Coding Agent 到 LLM 的消息架构](4.message-architecture-from-coding-agent-to-llm.md)，Compaction 和分支摘要的生成策略可参考[上下文工程](6.context-engineering.md)。

## 1. 先给结论

Pi 当前存在两套相关但不能混为一谈的会话系统：

| 层 | 当前实现 | 格式或后端 | 使用状态 |
|---|---|---|---|
| `packages/coding-agent` | `SessionManager` | 同步 JSONL，格式版本 v3 | 当前 Pi CLI、Interactive、Print、RPC 和 Coding Agent SDK 的实际会话实现 |
| `packages/agent/src/harness/session` | `SessionRepo`、`SessionStorage`、`Session` | 异步后端接口；已有 JSONL v4 和 SQLite 后端 | Agent Harness 的可替换会话基础设施 |

对当前 Coding Agent，可以先建立下面这个心智模型：

```text
物理存储：按发生顺序不断追加的 JSONL 日志
逻辑结构：由每条 entry 的 id / parentId 连接成的树
当前位置：内存中的 leafId
模型上下文：从 leafId 回溯到根，再经过 Compaction 和 entry-to-message 投影得到的视图
```

关键点是：

> JSONL 文件保存长期事实，`parentId` 表达历史关系，`leafId` 表达当前工作位置，LLM 只看到从整棵树计算出来的当前分支视图。

分支不会复制或删除原历史；Compaction 也不会删除原消息。两者都通过追加新 entry 表达新的事实。

## 3. 会话保存在哪里

Coding Agent 默认将会话保存在：

```text
~/.pi/agent/sessions/--<编码后的工作目录>--/
```

例如工作目录为：

```text
D:\Coding\PythonProjects\pi-agent-learning
```

默认会话目录为：

```text
C:\Users\<user>\.pi\agent\sessions\--D-Coding-PythonProjects-pi-agent-learning--\
```

编码规则是：

1. 将工作目录转为绝对路径。
2. 去掉开头的 `/` 或 `\`。
3. 把 `/`、`\`、`:` 替换为 `-`。
4. 在结果两侧加 `--`。

每个会话对应一个文件：

```text
<ISO 时间戳>_<session-id>.jsonl
```

例如：

```text
2026-08-31T01-23-45-678Z_01995f6b-8af2-7b12-9c01-9f3e9b580dea.jsonl
```

会话目录的选择优先级是：

```text
--session-dir
  > PI_CODING_AGENT_SESSION_DIR
  > settings.json 中的 sessionDir
  > 默认目录 ~/.pi/agent/sessions/--<cwd>--/
```

使用 `--no-session` 时，`SessionManager.inMemory()` 仍维护同样的 entry 树，但不创建文件，进程结束后数据消失。

## 4. JSONL 中保存了什么

JSONL 是 JSON Lines：文件中的每一行都是一个独立 JSON 对象。第一行是 header，后续每一行是一条 entry。

### 4.1 Header：描述整个会话

```json
{"type":"session","version":3,"id":"01995f6b-8af2-7b12-9c01-9f3e9b580dea","timestamp":"2026-08-31T01:23:45.678Z","cwd":"D:\\Coding\\PythonProjects\\pi-agent-learning"}
```

主要字段：

| 字段 | 含义 |
|---|---|
| `type` | 固定为 `session` |
| `version` | 当前 Coding Agent 格式版本为 3 |
| `id` | 会话 UUIDv7，也可以由 `--session-id` 指定 |
| `timestamp` | 会话创建时间 |
| `cwd` | 创建会话时的工作目录 |
| `parentSession` | 通过 fork、clone 等方式创建时，可指向来源会话文件 |

Header 不属于会话树，因此没有 `id` 之外的 entry ID，也没有 `parentId`。

### 4.2 Entry：描述一个不可变的会话事实

除 header 外，所有 entry 都有共同字段：

```ts
interface SessionEntryBase {
  type: string;
  id: string;
  parentId: string | null;
  timestamp: string;
}
```

其中：

- `id` 是当前 entry 的唯一 ID，通常是 8 位十六进制短 ID。
- `parentId` 指向逻辑父节点；第一条 entry 为 `null`。
- `timestamp` 是 entry 创建时间。
- `type` 决定剩余 payload 的结构和解释方式。

文件中的行号只代表提交顺序。真正的对话顺序必须沿 `parentId` 读取，不能简单地把整个文件当作线性消息数组。

### 4.3 内存中的索引

`SessionManager` 打开文件后会同时维护：

```text
fileEntries       header + 所有 entry，保持文件顺序
byId              entry id → entry 的 Map
labelsById        target entry id → 当前 label
leafId            当前活动叶子
```

`byId` 让父链回溯不必反复扫描整个数组；`leafId` 决定当前从哪条路径继续追加。

## 5. 一个完整会话如何长成树

下面使用一段字段结构真实、内容经过缩短的会话。所有 entry 类型、父子关系和写入顺序都对应当前 v3 实现；为便于阅读，省略消息内部完整的 `usage.cost` 等字段。

场景是：用户先让 Agent 设计 JSON 文件存储，沿这个方向继续后，又回到共同节点，改为 SQLite 方案。

### 5.1 第一轮：形成一条直线

用户发送第一条消息：

```json
{"type":"message","id":"e1a00001","parentId":null,"timestamp":"2026-08-31T01:23:46.000Z","message":{"role":"user","content":"为任务列表设计持久化方案","timestamp":1788139426000}}
```

模型请求读取现有代码：

```json
{"type":"message","id":"a1b00002","parentId":"e1a00001","timestamp":"2026-08-31T01:23:47.000Z","message":{"role":"assistant","content":[{"type":"text","text":"我先检查当前模型。"},{"type":"toolCall","id":"call_1","name":"read","arguments":{"path":"src/tasks.ts"}}],"provider":"openai","model":"gpt-5","usage":{"input":900,"output":80,"totalTokens":980},"stopReason":"toolUse","timestamp":1788139427000}}
```

工具结果作为独立消息保存：

```json
{"type":"message","id":"c1c00003","parentId":"a1b00002","timestamp":"2026-08-31T01:23:47.100Z","message":{"role":"toolResult","toolCallId":"call_1","toolName":"read","content":[{"type":"text","text":"export interface Task { ... }"}],"isError":false,"timestamp":1788139427100}}
```

模型给出 JSON 文件方案：

```json
{"type":"message","id":"a2d00004","parentId":"c1c00003","timestamp":"2026-08-31T01:23:49.000Z","message":{"role":"assistant","content":[{"type":"text","text":"建议先使用 append-only JSON 文件。"}],"provider":"openai","model":"gpt-5","usage":{"input":1300,"output":240,"totalTokens":1540},"stopReason":"stop","timestamp":1788139429000}}
```

此时逻辑树还是一条链：

```text
u1 user
└─ a1 assistant(toolCall)
   └─ t1 toolResult
      └─ a2 assistant(JSON 方案)  ← leafId
```

每次调用 `_appendEntry()` 都把新 entry 的 `parentId` 设为当前 `leafId`，随后把 `leafId` 更新为新 entry，因此普通对话自然形成线性父链。

### 5.2 沿 JSON 方案继续

用户继续让 Agent 实现 JSON 版本：

```json
{"type":"message","id":"e2e00005","parentId":"a2d00004","timestamp":"2026-08-31T01:24:10.000Z","message":{"role":"user","content":"按这个 JSON 方案实现","timestamp":1788139450000}}
{"type":"message","id":"a3f00006","parentId":"e2e00005","timestamp":"2026-08-31T01:24:30.000Z","message":{"role":"assistant","content":[{"type":"text","text":"JSON 版本已实现。"}],"provider":"openai","model":"gpt-5","usage":{"input":2200,"output":600,"totalTokens":2800},"stopReason":"stop","timestamp":1788139470000}}
```

树继续增长：

```text
u1
└─ a1
   └─ t1
      └─ a2
         └─ u2 user: 按 JSON 方案实现
            └─ a3 assistant: JSON 版本已实现  ← leafId
```

### 5.3 回到共同节点并创建分支

用户打开 `/tree`，从 `a3` 所在路径返回 `a2`。如果直接导航而不生成摘要，`SessionManager.branch("a2d00004")` 只在内存中把：

```text
leafId = "a2d00004"
```

下一条用户消息就会成为 `a2` 的另一个孩子。

如果用户选择“总结离开的分支”，Pi 会先追加 `branch_summary`：

```json
{"type":"branch_summary","id":"b1a00007","parentId":"a2d00004","timestamp":"2026-08-31T01:25:00.000Z","fromId":"a3f00006","summary":"离开的分支实现了 JSON 文件版本，修改了 tasks.ts，并加入了原子重命名。"}
```

然后用户在该摘要之后提出新方向：

```json
{"type":"message","id":"e3b00008","parentId":"b1a00007","timestamp":"2026-08-31T01:25:10.000Z","message":{"role":"user","content":"改用 SQLite，并保留相同接口","timestamp":1788139510000}}
{"type":"message","id":"a4c00009","parentId":"e3b00008","timestamp":"2026-08-31T01:25:30.000Z","message":{"role":"assistant","content":[{"type":"text","text":"SQLite 版本应把 TaskRepository 作为边界。"}],"provider":"openai","model":"gpt-5","usage":{"input":1900,"output":420,"totalTokens":2320},"stopReason":"stop","timestamp":1788139530000}}
```

文件的物理顺序仍是：

```text
u1 → a1 → t1 → a2 → u2 → a3 → s1 → u3 → a4
```

但 `parentId` 表达的逻辑树已经是：

```text
u1 user
└─ a1 assistant(toolCall)
   └─ t1 toolResult
      └─ a2 assistant(JSON 方案)
         ├─ u2 user: 按 JSON 方案实现
         │  └─ a3 assistant: JSON 版本已实现
         └─ s1 branch_summary: 离开分支做了什么
            └─ u3 user: 改用 SQLite
               └─ a4 assistant: SQLite 方案  ← leafId
```

这说明两个重要事实：

1. 物理上较晚写入的 `s1` 可以把 `parentId` 指向较早的 `a2`。
2. 旧的 `u2 → a3` 分支仍在文件中，没有被截断、覆盖或复制。

如果没有选择分支摘要，树中不会出现 `s1`，`u3.parentId` 会直接等于 `a2`。

### 5.4 分支、fork 和 clone 不一样

| 操作 | 文件数量 | 保存范围 | 典型用途 |
|---|---|---|---|
| `/tree` 导航或原地分支 | 仍是同一个文件 | 完整树 | 在同一任务中探索多个方向 |
| `/fork` | 创建新文件 | 从选定位置复制一条路径 | 将旧节点变成独立任务 |
| `/clone` | 创建新文件 | 当前活动分支 | 在当前成果基础上独立继续 |
| `createBranchedSession()` | 创建新文件 | 根到指定 leaf 的路径 | 从复杂树中抽出单条路径 |

新文件的 header 会生成新 session ID，并通过 `parentSession` 记录来源文件。原 entry ID 可以保留，因为它们现在处于另一个会话命名空间中。

## 6. 树上有哪些 Entry

Coding Agent v3 的 `SessionEntry` 是下面九种类型的联合。

| Entry type | 保存内容 | 是否直接进入 LLM 上下文 | 主要用途 |
|---|---|---|---|
| `message` | 一个 `AgentMessage` | 视 message role 而定 | 用户、助手、工具结果和 Bash 执行等消息 |
| `model_change` | `provider`、`modelId` | 否 | 恢复当前模型设置 |
| `thinking_level_change` | `thinkingLevel` | 否 | 恢复当前推理级别 |
| `compaction` | `summary`、`firstKeptEntryId`、`tokensBefore` 等 | 是，转成 `compactionSummary` | 用摘要替代较老上下文 |
| `branch_summary` | `fromId`、`summary` 等 | 是，转成 `branchSummary` | 把离开分支的重要成果带到新分支 |
| `custom` | `customType`、任意 JSON 数据 | 否 | Extension 持久化自己的状态 |
| `custom_message` | `customType`、content、display、details | 是，转成 `CustomMessage` | Extension 注入模型可见内容 |
| `label` | `targetId`、`label` | 否 | 给任意树节点设置或清除书签 |
| `session_info` | 当前会话名称 | 否 | `/name` 与会话选择器展示 |

### 6.1 `message` 中不只有文本

`message.message` 保存的是 `AgentMessage`。常见角色包括：

- `user`：字符串或文本、图片内容块。
- `assistant`：文本、thinking、ToolCall、模型/provider、usage、费用、停止原因。
- `toolResult`：ToolCall ID、工具名、文本或图片结果、错误状态和可选 details。
- `bashExecution`：用户直接执行的命令、输出、退出码、是否截断及完整输出文件路径。

因此会话文件可能包含用户输入、模型 thinking、工具参数、工具输出和 Shell 输出。它是明文 JSONL，不应假设其中没有敏感信息。

### 6.2 Entry 和 Message 为什么分开

如果文件中只能保存 Message，就无法自然表达：

- “用户把模型从 A 切到了 B”。
- “这个节点被标记为 checkpoint”。
- “较早历史已经被摘要，但原文仍保留”。
- “Extension 需要恢复内部状态，但不应把状态发给模型”。

Entry 是会话事实协议，Message 是对话协议。把两者分开，持久化层可以保存比 LLM transcript 更丰富的产品状态。

## 7. Append-only 是什么

Append-only 指正常运行时不修改已经提交的历史 entry，而是把每次变化写成一条新记录追加到文件末尾。

它不等于“文件永远不允许重写”。当前实现仍会在格式迁移、显式抽取分支等维护场景重写或创建文件。更准确地说：

> 正常会话演化遵循逻辑 append-only；已经提交的 entry 作为历史事实保持不变。

### 7.1 Pi 如何实现

`SessionManager.appendMessage()` 等方法先构造 entry：

```ts
const entry = {
  type: "message",
  id: generateId(this.byId),
  parentId: this.leafId,
  timestamp: new Date().toISOString(),
  message,
};
```

随后 `_appendEntry()` 完成三件事：

```text
fileEntries.push(entry)
byId.set(entry.id, entry)
leafId = entry.id
```

最后 `_persist()` 使用：

```ts
appendFileSync(sessionFile, `${JSON.stringify(entry)}\n`);
```

把 entry 追加为新的一行。

### 7.2 第一条 assistant 消息是延迟落盘边界

新建会话时，Pi 会立即在内存中创建 header 和目标文件名，但不会马上创建文件。

```text
newSession()
  → 内存中只有 header
用户 message_end
  → 用户 entry 暂存在内存
第一条 assistant message_end
  → header + 已有 entries 一次性创建并写入文件
之后的 entry
  → 每条直接追加
```

这避免会话列表中出现大量“启动后没有得到任何回答”的空会话。代价是：如果第一条 assistant 消息完成前进程退出，这个新会话通常不会留下文件。

### 7.3 更新名称和标签也是追加

Append-only 系统一般不原地更新旧事实。例如：

```text
session_info(name = "初始名称")
session_info(name = "数据库重构")
```

读取时取最后一条 `session_info`，得到当前名称。

Label 也是同样的“latest wins”语义：

```text
label(targetId = a2, label = "checkpoint")
label(targetId = a2, label = undefined)  // 清除标签
```

历史上何时设置、何时清除仍可从日志中恢复。

### 7.4 为什么选择 Append-only

它解决的是“需要同时保存完整历史和多分支路径”的问题。

具体收益：

1. **分支自然**：新 entry 只需指向任意旧节点，不需要复制公共前缀。
2. **写入简单**：常规提交是一行顺序追加，不需要随机修改大文件中间位置。
3. **保留历史**：重命名、标签、压缩和分支都不会抹掉之前发生的事实。
4. **扩展友好**：Extension 可以追加自己的 `custom` entry，并在重载时重放状态。
5. **便于诊断**：文件本身就是按提交顺序排列的事件账本，可以直接检查。

对应代价：

1. 文件只增不减，Compaction 降低的是上下文大小，不是磁盘文件大小。
2. Coding Agent v3 打开文件时会把所有 entry 加载到内存，超长会话的启动成本随文件增长。
3. “当前名称”“当前标签”等值需要通过回放或辅助索引计算。
4. v3 实现没有数据库式事务和 writer lease，不适合多个进程同时写同一个文件。
5. `appendFileSync()` 返回不等于底层设备已经执行 `fsync`；突然断电仍可能留下不完整尾行。

Agent 层较新的 JSONL v4 对最后一行 torn write 提供了修复逻辑，而 SQLite 后端使用事务、全局序列和 writer lease 加强并发与恢复语义。

## 8. 核心操作如何改变会话

### 8.1 创建与打开

| 方法 | 行为 |
|---|---|
| `SessionManager.create(cwd, sessionDir?)` | 创建新的持久化会话 |
| `SessionManager.inMemory(cwd?)` | 创建同结构但不落盘的会话 |
| `SessionManager.open(path, ...)` | 加载指定文件、迁移旧版本、重建索引 |
| `SessionManager.continueRecent(cwd, ...)` | 打开当前项目最近的会话；没有则新建 |
| `SessionManager.list()` | 列出当前 cwd 下的会话 |
| `SessionManager.listAll()` | 跨项目列出会话 |

打开已有文件时，Pi 会解析每行、执行 v1 → v2 → v3 迁移、建立 `byId` 和 label 索引，并把最后一条 entry 设为当前 leaf。

### 8.2 追加

主要追加方法包括：

```text
appendMessage()
appendModelChange()
appendThinkingLevelChange()
appendCompaction()
branchWithSummary()
appendCustomEntry()
appendCustomMessageEntry()
appendLabelChange()
appendSessionInfo()
```

`AgentSession` 把最终 `message_end` 当作消息提交边界：partial streaming update 用于 UI，不会反复写入会话；完整 user、assistant 和 toolResult 才会成为正式 entry。

### 8.3 原地导航和分支

`branch(entryId)` 只改变内存中的 `leafId`。下一次追加才会把新的路径持久化出来。

`branchWithSummary(entryId, summary, ...)` 则先把 leaf 移到目标节点，再追加一条 `branch_summary`。这条摘要既标记新路径，也可以进入后续 LLM 上下文。

### 8.4 Fork 和抽取分支

`forkFrom()` 创建一个新 session ID 和新文件，写入带 `parentSession` 的 header，然后复制来源 entry。

`createBranchedSession(leafId)` 只保留从根到指定 leaf 的路径。由于 label 自己也是树节点，抽取时需要移除旧 label entry、重新连接保留节点，并为仍有效的 label 创建新 entry。

### 8.5 Compaction

Compaction 追加一条：

```ts
{
  type: "compaction",
  summary,
  firstKeptEntryId,
  tokensBefore,
}
```

旧 entry 不删除。`firstKeptEntryId` 表示哪些近期原始消息仍应与 summary 一起发送给模型。

### 8.6 删除

删除会话是删除整个 `.jsonl` 文件，不是向会话树追加 tombstone。Interactive 会话选择器在可用时优先调用系统 trash 工具，使删除可恢复。

## 9. 如何把会话树转成 LLM 上下文

整个转换分为四步：

```text
完整 SessionEntry 树
  → 选择当前 leaf 的祖先路径
  → 应用最新 Compaction 的保留规则
  → SessionEntry 投影成 AgentMessage
  → transformContext / convertToLlm
  → Provider 无关的 Message[]
```

### 9.1 从 leaf 回溯到根

`buildSessionPath()` 从当前 `leafId` 开始：

```text
current = byId.get(leafId)
while current exists:
  path.push(current)
  current = byId.get(current.parentId)
path.reverse()
```

对于前面的分支示例，leaf 为 `a4` 时得到：

```text
u1 → a1 → t1 → a2 → s1 → u3 → a4
```

不会选中另一个分支上的：

```text
u2 → a3
```

因此“文件中存在”不等于“当前模型可见”。

### 9.2 应用最新 Compaction

如果当前路径上没有 Compaction，全部路径进入下一步。

如果存在 Compaction，`buildContextEntries()` 选择路径上最新的一条，并构造：

```text
compaction entry
+ 从 firstKeptEntryId 开始的压缩前保留 entry
+ compaction 之后新追加的 entry
```

更老且已经被 summary 覆盖的消息仍在文件中，但不会再进入当前 LLM 上下文。

### 9.3 Entry 投影成 AgentMessage

投影规则如下：

| SessionEntry | 投影结果 |
|---|---|
| `message` | 取出其中保存的 `AgentMessage` |
| `compaction` | `CompactionSummaryMessage` |
| `branch_summary` | `BranchSummaryMessage` |
| `custom_message` | `CustomMessage` |
| `model_change` | 不生成消息，只用于恢复 model |
| `thinking_level_change` | 不生成消息，只用于恢复 thinking level |
| `custom` | 不生成消息 |
| `label` | 不生成消息 |
| `session_info` | 不生成消息 |

同时，Pi 会扫描完整活动路径，恢复最后使用的 model 和 thinking level。AssistantMessage 本身也能提供最后实际响应的 provider/model。

`buildSessionContext()` 最终返回：

```ts
interface SessionContext {
  messages: AgentMessage[];
  thinkingLevel: string;
  model: { provider: string; modelId: string } | null;
}
```

### 9.4 AgentMessage 还不是最终 Provider 请求

Session 只负责恢复产品层的 `AgentMessage[]`。真正请求 LLM 前还会经过：

1. `transformContext`：Extension 可针对本次请求裁剪或修改 AgentMessage 视图。
2. `convertToLlm`：把 Coding Agent 自定义消息转换或过滤成 `user / assistant / toolResult`。
3. Provider adapter：再转换成 OpenAI、Anthropic、Google 等厂商的 wire payload。

System prompt 和 tool schemas 也属于最终请求上下文，但它们不是 Session 树中的 message；它们由运行时资源和当前工具注册表重新组装。

### 9.5 用前面的树做一次投影

当前 leaf 为 SQLite 分支的 `a4`：

```text
Session path
u1 → a1 → t1 → a2 → s1 → u3 → a4
```

投影后的 AgentMessage 近似为：

```text
user("为任务列表设计持久化方案")
assistant(toolCall read)
toolResult("export interface Task ...")
assistant("建议先使用 append-only JSON 文件")
branchSummary("离开的分支实现了 JSON 文件版本...")
user("改用 SQLite，并保留相同接口")
assistant("SQLite 版本应把 TaskRepository 作为边界")
```

JSON 实现分支的 `u2/a3` 不会进入上下文；它的信息只有在用户选择生成 `branch_summary` 时，才以摘要形式进入新分支。

## 10. Agent 层提供的可替换接口

`packages/agent/src/harness/session` 把会话能力分成四层。

### 10.1 `SessionRepo`：会话集合和生命周期

```ts
interface SessionRepo<TMetadata, TCreateOptions, TListOptions> {
  create(options: TCreateOptions): Promise<Session<TMetadata>>;
  open(metadata: TMetadata): Promise<Session<TMetadata>>;
  list(options?: TListOptions): Promise<TMetadata[]>;
  delete(metadata: TMetadata): Promise<void>;
  fork(source: TMetadata, options: ForkOptions & TCreateOptions): Promise<Session<TMetadata>>;
}
```

它管理的是一组会话：创建、发现、打开、删除和 fork。文件目录、数据库文件或远程服务地址都属于具体 Repo 的 metadata 和配置。

### 10.2 `SessionStorage`：单个会话的持久化 SPI

SPI 是 Service Provider Interface，即后端实现者需要满足的接口。`SessionStorage` 负责：

- metadata 读取。
- lane 创建、移动和 leaf 查询。
- entry 与 operation record 的追加。
- 按全局顺序或指定分支查询。
- 会话名称和 label 等 latest-value facts。
- token、费用和消息数统计。

它是自定义数据库后端最主要的实现边界。

### 10.3 `Session`：后端无关的业务外壳

`Session` 接收一个 `SessionStorage`，提供：

- JSON 可序列化校验。
- ID 生成。
- `appendMessage()`、`appendCustomEntry()` 等便捷方法。
- 查询参数校验。
- `view(lane)` 生成绑定到另一条 lane 的 `SessionTree` 视图。

因此数据库后端不需要重复这些通用业务规则，通常只需：

```ts
return new Session(databaseStorage);
```

### 10.4 `SessionTree`：消费方看到的窄接口

`SessionTree` 面向只需要操作一棵会话树的调用方，暴露 leaf、entry、branch query、name、label、stats 和基本 append。它不包含 Repo 的 list/delete/fork，也不暴露全部底层写入细节。

### 10.5 Lane、Entry、Record 和 Fact

新的接口比 Coding Agent v3 `SessionManager` 多了几类概念：

| 概念 | 作用 |
|---|---|
| Lane | 一个有名字、可移动的 leaf 指针；`main` 是默认 lane，可支持并行任务路径 |
| Entry | 构成会话树的长期内容节点 |
| Record | run、tool、queue、abort、usage 等操作账本；不等于上下文节点 |
| Fact | name、label 等 latest-value 全局事实 |
| `seq` | 后端分配的全会话提交序号，用于稳定排序、游标和并发线性化 |

这使“对话内容树”和“运行恢复日志”分离：Entry 决定上下文，Record 记录一次 operation 如何进行以及是否完成。

## 11. Coding Agent 现状与 Agent 接口的差异

| 维度 | Coding Agent `SessionManager` | Agent Harness Session 接口 |
|---|---|---|
| API 风格 | 同步方法 | 异步 Promise |
| 默认格式 | JSONL v3 | JSONL v4；也有 SQLite |
| 父节点分配 | `SessionManager` 用当前 `leafId` 设置 | Storage 根据目标 lane 的 leaf 原子设置 |
| 顺序 | 文件顺序，没有显式 `seq` | 后端分配全局 `seq` |
| 当前路径 | 单个 `leafId` | 一个或多个 lane |
| 运行日志 | 主要保存在 message/entry 中 | Entry 与 operation Record 分离 |
| name/label | 作为树上的 entry | 作为 append-only fact |
| 并发保护 | 没有 writer lease | 后端需线性化写入；SQLite 已有 writer lease |
| Compaction tail | `firstKeptEntryId` 引用旧 entry | `retainedTail` 直接保存保留的 AgentMessage |

因此不能把 v3 文件直接改名为 v4，也不能仅把一个 `SessionRepo` 实例传给当前 Coding Agent CLI 就完成替换。要让 CLI 使用新后端，需要在 Coding Agent 的装配边界引入该接口，或提供一个把新 `Session` 适配为当前 `SessionManager` 消费面的方法。

## 12. 如果要把会话存入自己的数据库

优先参考现有 [`SqliteSessionRepository`](../../packages/session-backends/sqlite-node/src/sqlite/repo.ts)，而不是重新设计一套不兼容协议。

实现一个新数据库后端的大致步骤是：

1. 定义 `MySessionMetadata`、create options 和 list options。
2. 实现 `SessionRepo` 的 `create/open/list/delete/fork`。
3. 为单个会话实现 `SessionStorage`。
4. Repo 在 `create/open` 时构造 Storage，并返回 `new Session(storage)`。
5. 使用事务实现 entry append：读取 lane leaf、分配唯一 `seq`、写入 entry、移动 lane leaf，四步必须原子完成。
6. 为 entry ID 和 record ID 建立会话内唯一约束。
7. 实现 branch query、游标、类型过滤和稳定顺序。
8. 把 name、label、usage 等建模为 append-only fact/record，或维护可由事实日志重建的派生表。
9. 明确单写者或多写者语义；若只允许单写者，应实现 lease、fencing token 或等价机制。
10. 运行 `createSessionBackendConformance()` 生成的后端一致性用例。

最关键的事务近似为：

```text
BEGIN
  currentParent = SELECT leaf_id FROM lanes WHERE session_id = ? AND lane = ?
  seq = allocateNextSequence(session_id)
  INSERT entry(id, parent_id = currentParent, seq, payload, ...)
  UPDATE lanes SET leaf_id = entry.id
COMMIT
```

Promise 只能在数据库已经持久接受这次写入之后 resolve。否则 Agent 可能认为 entry 已提交并继续产生子节点，而数据库中实际没有它的父节点。

现有 SQLite 后端已经演示了推荐拆表方式：

```text
sessions             会话元数据
entries              树节点和 payload
lanes                当前命名 leaf
records              operation/run/tool/usage 日志
facts                name、label 等 latest-value 事实
session_sequences    全局 seq 分配
session_stats        派生统计
branch_entries       分支查询缓存
writer_leases        单写者租约与 fencing
```

如果目标只是“让当前 Coding Agent CLI 立即保存到业务数据库”，还需要额外完成产品层接线。推荐方向是让 Coding Agent 依赖 `SessionTree`/`SessionRepo`，再保留 v3 `SessionManager` 作为兼容适配器；直接复制 `SessionManager` 并把每个文件操作替换为 SQL，会继续制造第二套难以统一的会话语义。

## 13. 数据安全与故障边界

会话文件或数据库可能保存：

- 用户输入和图片。
- Assistant 文本、thinking、ToolCall 参数和 usage/cost。
- ToolResult、命令输出和错误信息。
- Extension 的 `custom` 数据。
- 工作目录、模型和分支摘要。

因此会话存储应被当作敏感应用数据处理。数据库实现至少应考虑：

1. 数据库文件和备份的访问权限。
2. 日志、搜索索引和导出文件是否复制了敏感内容。
3. 删除会话时是否同步处理派生索引。
4. Payload schema 升级和旧版本迁移。
5. 突然终止、事务回滚和重复重试的幂等性。
6. 多进程写入时如何防止旧 writer 在 lease 失效后继续提交。

## 14. 最小心智模型

可以用下面六句话概括 Pi 的会话管理：

1. Coding Agent 当前把一次会话保存成一个 JSONL v3 文件。
2. 文件是按提交顺序追加的日志，`id/parentId` 才定义逻辑树。
3. 普通追加沿当前 `leafId` 生长；回到旧节点后追加就形成新分支。
4. Branch Summary 和 Compaction 都是新增 entry，不会删除原始历史。
5. 发给 LLM 的不是整个文件，而是“当前 leaf 父链 + Compaction 规则”的消息投影。
6. Agent Harness 已把会话抽象为可替换的 `SessionRepo`/`SessionStorage`；数据库后端应实现这组契约，并在 Coding Agent 产品层完成接线。
